# Routing portable rules

Suggested text for personal agent instructions. It neither installs skills nor changes settings; applying it is a separate user-requested action. Catalog descriptions help selection but do not guarantee loading. Explicitly name the skill and verify its use when it matters.

## Suggested instructions

```text
Start with the current task and applicable repository instructions.
Choose an available domain skill by the work: vue-nuxt-workflow for Vue/Nuxt
and related state/data, scss-workflow for styling, go-backend-workflow for
Go backend. Read detailed references only when changing the relevant area.

Use project-foundation for creating, organizing, learning, or substantially
changing project boundaries. Use project-memory for durable decisions and
context when the task needs it. Neither is a mandatory step before local edits.

Use scenario-review for an explicit proposal review or a consequential unresolved
scenario that could change an important decision. Do not repeat an equivalent
completed review. Routine edits need no chain of skills, separate plan, or
architecture audit.

Domain skills supply portable criteria and conventions; the repository supplies
adopted mechanisms, contracts, paths, and commands. Reuse those mechanisms.
Do not copy another project's structure merely because a skill uses it as an
example. The explicit current request defines scope. Surface material conflicts
with local rules rather than silently rewriting them.

If a needed skill is unavailable, say so; do not pretend to apply it. Continue
with available instructions if the task remains feasible. If the user requires
that skill and the task cannot proceed without it, explain what is missing.
Do not install tools or change settings to bypass a missing skill without
authorization.
```

## Where rules belong

| Location | Content |
| --- | --- |
| Personal instructions | Preferences and selection of available skills |
| Domain skill | Portable requirements and decision criteria |
| References | Conditional detail and examples |
| Repository | Accepted decisions, local APIs, paths, commands, and process |

Maintain one version of each skill, without basic/extended splits. Short essential invariants can also appear in a repository so it remains usable without a personal installation. Long procedures need one owner; a project must not depend on private-directory files. Routing helps retain relevant rules but does not guarantee model behavior or replace verification.
