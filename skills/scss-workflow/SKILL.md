# Работа с SCSS

Используй отобранные удачные приёмы, а не средний стиль репозитория. Даже в
хорошем компоненте могут соседствовать полезная схема состояний, лишняя
вложенность и неудачные переопределения. Заимствуй конкретное решение вместе
с условиями его применения; не объявляй весь файл эталоном.

Это дополнение к соглашениям проекта. Имена токенов и API ниже относятся к
Digiversity; в другом проекте сначала найди их местные аналоги. Не превращай
обычную правку в миграцию дизайн-системы или аудит всего фронтенда.

## Сначала установи контекст

- Прочитай инструкции проекта, шаблон и стили компонента, его consumers и
  ближайшие удачные аналоги. Для CSS-класса ищи также внешние селекторы,
  динамические bindings, slots и fallthrough attributes.
- Проверь источник токенов, глобальную точку подключения CSS и
  `css.preprocessorOptions.scss.additionalData`. Не предполагай, что каждый
  Vite/Nuxt entrypoint подключает один и тот же Sass API.
- Раздели визуальное изменение и сохранение текущей отрисовки. В Digiversity
  для изменения визуала действуют требования текущих `AGENTS.md`: Figma и
  явное одобрение конкретного изменения. Этот скилл такого одобрения не даёт
  и не переносит локальный порядок согласования на другие проекты.

## Токены и границы Sass

- Цвета выбирай по назначению: `--text-secondary-color`,
  `--secondary-border-color`, `--error-default-color`, а не по похожему HEX.
  Используй подходящие `--spacing-*`, `--radius-*`, `--effects-*`. Не меняй
  размер ради ближайшего токена; учитывай разницу `px` и `rem` при масштабировании.
- До использования найди объявление custom property и путь, по которому она
  доступна элементу: глобальный CSS, предок или inline style. Похожее имя из
  соседнего файла не доказывает существование токена. Fallback оправдан для
  действительно необязательного параметра, но не маскирует опечатку.
- CSS custom properties используй для значений, меняющихся через каскад,
  состояние или runtime. Sass-переменные — для compile-time констант, например
  порогов обычных viewport `@media`. Не подставляй туда `var(--breakpoint)`.
- В Digiversity `api.scss` предоставляет breakpoints, z-index и типографику
  без самостоятельного CSS. `global.scss` эмитит `:root`, шрифты, utilities и
  глобальные селекторы; ему место в общей точке входа, а не в каждом SFC или
  `additionalData`. Учитывай уже настроенный `@use ... as *`.
- Для явных Sass-зависимостей предпочитай `@use` с понятным namespace,
  `@forward` — для существующего публичного API. Не затевай массовую замену
  импортов при локальной задаче.
- Типографику бери из действующих классов или `typography(...)`. Особенность
  текущего Digiversity API: этот миксин вызывает `@extend` placeholder-а.
  Внутри `@media` он не компилируется; это не обычный миксин с декларациями.
  Адаптивную типографику решай по макету и доступному API, не копируя вслепую
  include под условие. Не расширяй чужие concrete-селекторы через `@extend`.

## Компонент, селекторы и состояния

- Предпочитай устойчивый корневой класс и локальные элементы/модификаторы:
  `.queue-screen`, `&__caption`, `&--allowed`. Вложенность SCSS должна
  сокращать запись, а не повторять всё DOM-дерево. Проверяй получившийся CSS:
  `&__title` и `.title` внутри блока дают разные селекторы и специфичность.
- Сохраняй существующий договор изоляции. Для нового закрытого SFC обычно
  подходит `scoped`; shared primitives, slots, teleports и внешние consumers
  требуют проверки. Добавление `scoped` или переименование класса не является
  автоматически безопасным рефакторингом.
- Если несколько частей зависят от одного состояния, задай на владельце
  небольшое семейство `--component-*`, а в модификаторе поменяй значения.
  Пример — `--field-border-color` и `--field-meta-color` в `fields/Base.vue`.
  Для единственного `color` достаточно прямой декларации: переменная нужна
  для реального переиспользования или контракта настройки.
- Используй реальные классы/атрибуты состояния из шаблона и props. Сохраняй
  приоритеты сочетаний `hover`, `active`, `focus-visible`, `disabled`, loading
  и ошибок. `:hover` для указателя ограничивай `(hover: hover)`, как в
  `fields/base/Input.vue`; клавиатурный focus от этого условия не зависит.
- Сначала используй props, slots и предусмотренные CSS-параметры дочернего
  компонента. Глубокий descendant selector, `:deep()` и `!important` требуют
  конкретной причины и проверки consumers. Не объявляй их ни нормой по
  частоте использования, ни безусловно запрещёнными.
- Не снимай `outline` без проверенного видимого focus на самом контроле или
  его оболочке. Не копируй сбросы из внутреннего Input отдельно от FieldsBase.

## Раскладка, адаптивность и повторение

- Базовую раскладку выражай flex/grid и `gap`. Если содержимое должно
  сжиматься, проверь `min-width: 0`/`min-height: 0` у соответствующего flex/grid
  item; фиксированным иконкам при необходимости оставляй `flex-shrink: 0`.
  Обрезание текста, перенос и прокрутка — разные решения, выбираемые по UX.
- Используй принятые breakpoints; индивидуальный порог допустим, когда его
  требует конкретный макет. Не округляй существующие границы ради единообразия.
  Локальное media-правило держи рядом с владельцем; общие для нескольких
  экранов параметры можно менять на layout через CSS variables.
- Динамическую геометрию передавай из JS небольшими параметрами, когда она
  зависит от данных. Обычную адаптивность раскладки оставляй CSS, если задача
  не требует менять состав или поведение интерфейса.
- Группируй одинаковые правила внутри одного владельца. Миксин выделяй для
  реального повторяемого набора с параметрами; shared-файл — для общего
  владельца нескольких consumers. Не создавай utility/framework для пары
  деклараций и не склеивай несвязанные компоненты ради одинакового `display`.
- Анимируй нужные свойства явно. Пользуйся имеющимися transitions, если
  совпадает их поведение; не копируй `transition: all` и не меняй существующие
  duration/easing под видом уборки.

## Примеры и проверка

Для конкретного решения прочитай соответствующий раздел
[references/examples.md](references/examples.md): состояния, вложенность,
адаптивные параметры, Sass API/типографика или карта отобранных исходников.
Там отделены удачные фрагменты от соседних приёмов, которые копировать не стоит.

- Перечитай весь свой diff: селекторы должны соответствовать DOM, все токены
  разрешаться, новые правила не вытекать в соседние компоненты. Не форматируй
  и не переименовывай несвязанный код.
- Проверь SCSS установленным компилятором через реальный pipeline проекта.
  ESLint/typecheck сами по себе этого не доказывают; Stylelint запускай, если
  он действительно настроен. Выполни обязательные проверки текущего проекта.
- При обещании сохранить отрисовку сравни CSS, полученный одинаковым
  pipeline до и после: значения, единицы, селекторы, специфичность, порядок,
  условия. Затем проверь затронутые состояния и нужные размеры окна в браузере;
  raw Sass-компиляция не заменяет обработку Vue scoped styles.
- В Digiversity runtime shared components читается из `dist`, а Sass API —
  из экспортированных SCSS-исходников. Для smoke проверь свежесть нужных
  артефактов и запуск необходимых API; Safari-дефект проверяй в WebKit.
- Для визуальной задачи проверь макет, узкую ширину, длинный текст и нужные
  состояния. При чистом рефакторинге не устраняй попутно старые визуальные
  недочёты: зафиксируй отдельный follow-up. Укажи, что фактически проверено.
