# Работа с Go backend

Применяй этот порядок при работе с Go. Он собран по коду Digiversity: критерии решений, затем конкретные примеры. Имена пакетов, команды и архитектурные ограничения проверяй по текущему проекту. Явные указания пользователя для задачи имеют приоритет; skill сам не вводит обязательный план, аудит, новый framework или разрешение на внешние действия.

## Перед изменением

- Прочитай действующие инструкции проекта для используемого агента (например, `AGENTS.md`/`CLAUDE.md`), целевой код и ближайший работающий аналог вместе с его тестами. Проверь владельца `go.mod`, локальные `replace`, наличие `go.work`, генераторы и конфигурацию проверок. Не предполагай, что команда из корня проверяет все модули.
- Проследи путь запроса: router/HTTP или NATS → сервис → запрос к БД/внешний клиент → ответ, событие или кеш. Найди вызывающие места и consumers изменяемого контракта. Исправляй общую причину в месте, через которое проходят затронутые сценарии.
- Сначала найди готовый helper, adapter, parser, тип ошибки и способ сборки зависимостей. Повторное подключение существующего API предпочтительнее второй реализации той же обязанности.
- В Digiversity прочитай [references/digiversity.md](references/digiversity.md): там текущие ориентиры по `gotemplate`, `gokit`, AuthN/AuthZ, sqlc и проверкам. В другом Go-проекте выясни его аналоги; не переноси автоматически Gin, NATS или Leino.

## Где должна жить логика

- Handler разбирает транспорт, вызывает сценарий и формирует ответ. В сервисе держи бизнес-валидацию, порядок операций и работу с данными. Передавай ему `context.Context` и прикладные аргументы; зависимость от `*gin.Context` в сервисный слой не добавляй.
- Выделяй функцию, пакет или интерфейс под самостоятельную ответственность и фактического потребителя. Тестовый fake — достаточный потребитель интерфейса, даже при одном production-адаптере. Интерфейс объявляй возле кода, который его использует; не строй общий `ports`-каталог ради симметрии.
- При принятом в проекте прямом доступе через sqlc используй генерённый `query.Querier`. Не дублируй его рукописным `store` и pass-through repository. Отдельный адаптер оправдан вторым источником данных, кешем или собственной семантикой; существующие слои не сноси в посторонней задаче.
- Одну прикладную форму Input/Patch используй в обоих сценариях HTTP и RPC. Сохраняй необходимое преобразование protobuf ↔ прикладной тип. Представление API может отличаться от строки БД: маппинг ради формата, сокрытия поля или агрегата полезен; копия каждого поля через несколько одинаковых structs — лишняя.
- Собирай зависимости в composition root, передавай через конструктор или `Deps`. После переделки убирай опустевшие обёртки, интерфейсы, мапперы и регистрации в затронутом коде.

## Как писать код

- Предпочитай ранний `return` и `continue`, обычные циклы и прямой поток данных. Простую сборку результата не превращай в generic pipeline с callbacks. Готовые понятные операции стандартной библиотеки используй, если они доступны в версии проекта.
- Для сбора `0..N` элементов выделяй `make([]T, 0, len(source))`, когда верхняя граница известна. Сохраняй порядок, дубликаты и формат пустого результата по контракту. В JSON `nil` и пустой slice могут означать разные ответы; `make([]T, len(source))` перед `append` добавляет лишние zero values.
- Сохраняй типизированные данные до транспортной границы. Не подменяй DTO через `map[string]any` или JSON round-trip ради удобства маппинга. При преобразовании внешнего числа в более узкий тип проверь допустимый диапазон; `int32(value)` сам ничего не валидирует.
- Валидацию, нужную HTTP и RPC, выполняй в общем сценарии. Проверка синтаксиса JSON или query остаётся в handler. Не нормализуй все пустые строки и нули одинаково: для конкретного поля они могут означать сброс, допустимое значение или ошибку.
- Комментарии добавляй для неочевидного контракта, причины исключения, конкурентного поведения или обязательного godoc/генератора. Очевидные шаги делай понятными через имена. Чужие комментарии вне задачи сохраняй.

## Ошибки, context и ресурсы

- Из HTTP передавай `c.Request.Context()`, из RPC — контекст вызова. Не заменяй их на `context.Background()` в обычной цепочке: отмена, deadline и tracing должны дойти до БД, HTTP-клиента и NATS. Созданный timeout освобождай через `defer cancel()`.
- Ошибки классифицируй через `errors.Is`/`errors.As`, при добавлении контекста сохраняй цепочку с `%w`. Отсутствующая строка, отказ доступа, недоступная зависимость и произвольная ошибка БД — разные исходы. Не возвращай пустой успешный результат при неожиданном отказе.
- Пользовательский ответ формируй принятым transport mapper. Подробности внутреннего отказа направляй в имеющийся logger/span; не отправляй клиенту SQL/внутренний `err.Error()` и не логируй ту же ошибку на каждом слое.
- Goroutine запускай при реальной необходимости. До запуска определи владельца, отмену, ограничение параллелизма, сбор ошибок и ожидание завершения. Для пакетного чтения сначала проверь существующий batch API; N независимых goroutines не исправляют N+1-запросы.
- У долгоживущего ресурса должен быть владелец закрытия, в том числе при частично неудачном startup. Cleanup после отмены родителя может требовать отдельного ограниченного контекста; не используй уже отменённый запрос для graceful shutdown и не создавай бессрочную фоновую работу. Переиспользуй lifecycle проекта.

## Данные и контракты

- В PATCH различай «не передано» и явные `false`, `0`, `""`. Если контракт отдельно поддерживает JSON `null`, обычного `*T` недостаточно: сохрани принятую в проекте информацию о присутствии поля. Не добавляй универсальный optional-framework для одного случая.
- Проверяй результат записи по контракту запроса: ноль изменённых строк может требовать `NotFound` или `Conflict`, даже если `err == nil`. Предварительное чтение само не гарантирует существование строки к моменту записи.
- Связанные изменения данных выполняй в одной транзакции; её запросы должны использовать transaction-bound queries (`WithTx` или аналог). Ошибку `Commit` возвращай. Событие об успешной записи отправляй после подтверждённого сохранения, сохраняя существующую семантику доставки; не называй best-effort уведомление гарантированным и не повторяй всю запись только из-за его отказа.
- Меняй источники генерации: SQL, migration, sqlc config, proto, swagger-аннотации. Затем запускай генератор владельца и проверяй итоговые типы и consumers. Файлы `Code generated`/`DO NOT EDIT` не правь вручную. Применённую migration не переписывай как обычный исходник.
- Для публичного контракта проверь не только компиляцию: JSON имена, `null`/`[]`, порядок, статусы, protobuf field numbers, subjects, retry/idempotency и реальные вызывающие стороны — в той части, которую меняет задача.

## Примеры решений

Прочитай нужный раздел [references/examples.md](references/examples.md) перед соответствующей правкой:

- «Handler и аутентификация» — parser, место guard и проверка router.
- «Сервис, sqlc и ошибка» — прямой `Querier`, полезный маппинг, типизированный отказ.
- «PATCH: отсутствует, false и null» — сохранение присутствия и контрактные проверки.
- «Сбор результата» — цикл, ёмкость slice и пустой JSON-массив.
- «Отмена и cleanup» — отдельный ограниченный контекст только для завершения ресурсов.
- «Тестовый шов без repository» — маленький fake и проверка наблюдаемого результата.

Примеры показывают критерий выбора и форму кода. Условия, импорты и доступность API сверяй с целевым модулем.

## Перед завершением

- Перечитай весь итоговый diff задачи: исходники, generated code, регистрацию зависимостей, тесты и конфигурацию. Проверь, что упрощение сохранило реальные consumers, обработку отказов и срок жизни ресурсов.
- Форматируй только свои Go-файлы. Запусти focused tests затронутого пакета, затем обязательные проверки проекта для модуля и его affected consumers. Не обновляй toolchain, не запускай `go get`/`go mod tidy` и генерацию всего проекта автоматически ради обычной правки.
- Для изменённого поведения выбери тест, который наблюдает результат: HTTP-ответ и вызов сценария, переданные параметры, отсутствие эффекта при отказе, rollback или отмену. SQL и транзакционные гарантии проверяй существующими integration-тестами, когда от них зависит изменение; fake не проверяет саму БД. Не добавляй фиктивные тесты на форму реализации или отдельный suite ради форматирования.
- Не включай `t.Parallel()` механически в тестах с глобальным logger, env или общим состоянием. При изменении конкурентности используй применимые race/cancellation-проверки, если среда их поддерживает.
- Сообщи результат, фактические проверки и существенное ограничение. Неподнятая зависимость, пропущенный integration-тест или скомпилированный fake не доказывают работу живого сервиса.
