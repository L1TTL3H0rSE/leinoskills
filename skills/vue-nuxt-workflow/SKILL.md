# Работа с Vue/Nuxt

Применяй этот порядок при работе с Vue/Nuxt. Ниже — постоянные предпочтения пользователя; конкретные имена библиотек, автоимпорты и структуру проекта выясняй по текущему репозиторию. Явные указания пользователя для задачи имеют приоритет. Не превращай обычную правку в отдельный аудит или обязательное согласование плана.

## Перед изменением

- Прочитай действующие инструкции проекта для используемого агента (например, `AGENTS.md`/`CLAUDE.md`), целевой код и ближайший аналог: компонент для компонента, композабл для композабла. Проверь конфигурацию автоимпортов и установленные версии, если изменение от них зависит.
- Найди все места использования изменяемой функции или компонента. Проследи путь от события или данных до эффекта в интерфейсе, включая создание и уничтожение экземпляра. Исправляй причину в общем месте, если она затрагивает несколько вызывающих мест.
- Найди существующий способ решить задачу: библиотечную модалку, стор, хелпер, композабл. Используй его API. Не создавай свою реализацию рядом с готовой без конкретной причины.
- Для неопределённого UX сначала сформулируй конкретное предложение, если пользователь просит согласовать его. Уже согласованную реализацию выполняй без повторных разрешений; обычные технические решения принимай по коду проекта.

## Где должна жить логика

- Оставляй в `.vue` шаблон, стили и минимальное подключение зависимостей. Логику поведения, подписок и преобразования данных размещай в `.ts` по принятому разделению проекта.
- Композабл выделяй по самостоятельной ответственности или жизненному циклу. Одно место использования допустимо; требование обязательного переиспользования не вводи. Общий стор используй для действительно общего состояния, а не для любой локальной переменной.
- Отдельный компонент должен владеть осмысленной частью интерфейса или поведением. Обёртка с одним `div`, которая только передаёт ref композаблу, обычно лишняя. Само количество строк не определяет полезность компонента.
- После смены решения пересмотри разделение. Например, после переноса окна в библиотечный стор удали опустевший компонент, его регистрацию, стили позиционирования и больше не нужные возвращаемые значения.
- Ресурс должен жить столько, сколько его владелец: звук встречи не должен зависеть от наличия карточки участника в раскладке. Сохраняй очистку треков, обработчиков и окон при завершении соответствующего жизненного цикла.

## Как писать код

- Используй подтверждённые автоимпорты. Не добавляй явные импорты Vue API и локальных композаблов, если они уже настроены. Нужные импорты библиотек и типов сохраняй; не предполагай, что Nuxt автоматически импортирует всё.
- Повторяй порядок ближайшего аналогичного композабла. Если образца нет: сторы и зависимости → состояние → вычисляемые значения → функции → watchers, подписки и lifecycle hooks → `return`. Учитывай зависимости и немедленный запуск watchers.
- Все тела `if`, `else`, `for`, `while` и `do` оформляй блоками `{}`, включая однострочные `return`, `continue`, `throw` и вызовы функций.
- Предпочитай ранний `return` и `continue` вложенной основной логике. Внутри циклов сначала отсеивай неподходящие элементы.
- Используй `watch` с явными источниками. Производные данные выражай через `computed`. Не вводи `watchEffect` в новом коде. При замене существующего watcher сохраняй нужные зависимости, момент запуска и очистку.
- Для последовательности действий с ошибками предпочитай `async/await` и `try/catch`. Не добавляй `void` перед Promise ради краткости. Если операция выполняется без ожидания, обоснуй необходимость в контексте поведения и обработай отказ. Переставляя `await`, проверь пользовательский жест браузера, смену состояния и размонтирование: завершившаяся старая операция не должна открывать устаревшую модалку.
- Не оставляй пустой `catch`. Используй принятое в проекте сообщение об ошибке или обработку ожидаемого отказа; учитывай уже существующую телеметрию, чтобы не дублировать её. Состояние загрузки сбрасывай в `finally`, когда операция может завершиться ошибкой.
- Не уплотняй обход вложенных коллекций цепочками `flatMap`, spread и тернарниками, возвращающими массив из одного элемента или пустой массив. Для такого сбора используй обычные циклы и `push`. Простые `map` и `filter` оставляй там, где они читаются прямо.
- Не добавляй новые поясняющие комментарии без запроса. Делай намерение понятным через имена и структуру; не удаляй чужие комментарии вне задачи.

## Интерфейс и браузеры

- Для кнопок, попапов и модалок сначала проверь существующие компоненты и примеры их подключения. Самостоятельное окно на нативном `dialog` не выбирай автоматически, если проект уже использует свою модалку.
- Продумай положение относительно существующих контролов, узкую ширину, небольшую высоту окна, длинный текст, прокрутку и fullscreen. Основное действие должно оставаться доступным.
- Закрываемость окна определяй по последнему запросу пользователя и реальным возможностям компонента. Если закрытие разрешено, не открывай окно немедленно заново из-за неизменившегося состояния.
- При проблеме Safari проверяй WebKit. Chromium сам по себе не подтверждает исправление. Для новых браузерных API и CSS проверь поддержку в целевых версиях по актуальной документации. Указывай ограничения среды: проверка DOM с имитацией треков не доказывает воспроизведение реального аудио.

## Перед завершением

- Перечитай весь итоговый diff задачи, включая ранее сделанные изменения, которые затронуты новым решением. Проверь соглашения, оставшиеся после переделки сущности, импорты, стили, refs и зависимости. Зелёные тесты не заменяют эту проверку.
- Не форматируй несвязанный код ради единообразия. Пользовательские предпочтения применяй к своему изменению и затронутым участкам.
- Запусти подходящие существующие проверки. Для простой перестановки или оформления кода не создавай отдельный тестовый файл. Не оставляй временные `.mjs`, стенды, скриншоты и диагностические логи в репозитории; постоянную регрессионную проверку добавляй по принятому в проекте подходу, когда она оправдана задачей.
- В ответе кратко укажи результат, выполненную проверку и существенное ограничение, если оно есть. Коммит, amend и push выполняй только в явно запрошенном объёме.
